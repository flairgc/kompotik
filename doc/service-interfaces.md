# Взаимодействие основного сервиса со специализированными

Статус: проект контрактов для обсуждения, не описание работающих интеграций. Дата: 25 сентября 2026 года.

Основа: [архитектура v0.5](architecture.md), [функциональные требования](https://docs.google.com/document/d/13DhyOBaIGAJRgvpVTTC32wxpCtCYCFFowQn9RIn3KDU/edit), [нефункциональные требования](https://docs.google.com/document/d/1c5UXA0RfIJ75Z2sQTfz0E-spPfpsIqhiP_baDNj83vI/edit). Новые поля и протоколы ниже — предложения. Связанные документы: [API клиента](api.md), [БД](database.md), [экраны](user-interface.md).

## 1. Границы ответственности

```text
                         Основное приложение
Клиент --> HTTP API --> PostgreSQL: предметные данные + jobs
                              ^                   |
                              |                   v
                              +--------------- worker
                                                  |
                        +-------------------------+-------------------+
                        |                         |                   |
                        v                         v                   v
                   Анализ текста             Изображения           Озвучка
                        |                         |                   |
                  Кандидаты смыслов               +------> S3 <-------+
                        |                                  |
                        +----> worker проверяет и публикует+
```

| Участник | За что отвечает | Что возвращает |
| --- | --- | --- |
| Основной API | Пользователь, права, папки, карточки/смыслы, прогресс, приём команд и выдача медиа. | Клиентские DTO и ID задания. |
| Worker основного приложения | Оркестрация, аренда заданий, вызовы адаптеров, проверка ответа, привязка результатов к карточкам, публикация ревизии. | Предметный результат в PostgreSQL. |
| Анализ текста | Выделение слов/выражений, лемматизация, определение употреблённого значения и вариантов сопоставления. | Кандидаты с контекстом, вхождениями и ссылками на смысл, а не готовые пользовательские папки. |
| Изображения | Получение изображения именно указанного смысла и сохранение файла в S3. | Метаданные файла, модель/источник, параметры операции. |
| Озвучка | Поиск допустимого готового аудио или синтез точной формы/диалекта, сохранение файла. | Метаданные аудио и фактического произношения. |

Сервис изображений — отдельный процесс по принятой архитектуре. Анализ текста и озвучка здесь имеют отдельные **логические контракты**; их можно реализовать адаптерами worker либо вынести в сетевые процессы. Последнее пока не утверждено. Контракт не требует отдельной БД предметных данных, брокера, Redis или GPU. При необходимости другого окружения предлагаются `apps/text-analysis-service` и `apps/audio-service`; они пока не создаются.

Клиент вызывает только основной API. Сервисы не меняют папки, прогресс, общие словарные смыслы или опубликованные карточки напрямую. Решение переиспользовать существующую карточку, создать приватную и показать её пользователю принимает основной сервер.

## 2. Общий протокол операций

Для сетевых реализаций предлагается одинаковая оболочка. Локальный адаптер worker реализует эквивалентные функции `submit/get/cancel`, без обязательного HTTP к самому себе.

| Метод внутреннего сервиса | Назначение |
| --- | --- |
| `PUT /internal/v1/operations/{operation_id}` | Принять операцию с неизменяемым телом. `202` для выполняющейся, `200` для повторно найденной завершённой. Тот же ID и другое тело — `409 OPERATION_PAYLOAD_CONFLICT`. |
| `GET /internal/v1/operations/{operation_id}` | Получить `state`, этап, результат/ошибку. Не запускает работу повторно. |
| `POST /internal/v1/operations/{operation_id}/cancel` | Запросить отмену; `202` если ожидается, `200` если уже отменена, `409` если завершилась. |
| `GET /health/live`, `GET /health/ready` | Работоспособность процесса и готовность принимать свою работу. |

У каждого сервиса свой base URL и поддерживаемый `kind`: `analyze_text`, `generate_image`, `generate_audio`. Общая оболочка запроса: `{contract_version: 1, kind, request_id, deadline_at, payload}`. `request_id` — трассировка сквозного задания; operation ID в пути. Повторяетcя исходное тело, включая deadline: попытка изменить параметры создаёт новую операцию. Секрет авторизации передаётся отдельно от JSON.

Ответ: `{operation_id, state, stage?, progress?, result?, error?, created_at, updated_at}`. Состояния:

```text
accepted --> running --> succeeded
    |          |
    |          +-----> failed
    |          |
    +----------+-----> cancelled
```

`cancel_requested` — флаг ожидания отмены, а не обещание уже остановленного провайдера. `progress` публикуется только при измеримых этапах. Ошибка: `{code, message, retryable, retry_after_seconds?, details?}`; результат и ошибка взаимоисключающие. Окончательный ответ неизменяем, идемпотентность сохраняется после рестарта сервиса.

Сетевой сервис хранит технический реестр операций: `operation_id PK`, `request_hash`, `kind`, `contract_version`, `state`, `payload`, `result`, `error`, `provider_request_id`, `cancel_requested`, `created_at`, `updated_at`, `expires_at`. Это его техническое хранилище, без копирования пользователей/карточек. На первом сервере допустима отдельная схема PostgreSQL с отдельной ролью; прямых прав на предметные таблицы у неё нет. Локальному адаптеру достаточно реестра основного worker с теми же гарантиями.

Запуск возвращает ответ после надёжного сохранения операции, а не после окончания AI-вызова. Основной worker опрашивает состояние с backoff; WebSocket, webhook и входящий callback не нужны в первом варианте. Передача результата через отдельный manifest допустима для больших ответов, но только в закрытом хранилище и с проверкой размера/хеша.

## 3. Анализ текста: вход

Нужно извлечь не только уникальные написания, а употребления значений. `went` и `go` могут вести к одной лексической единице, а `bank` в разных предложениях — к двум смыслам. `look up` — выражение, в том числе в разорванной форме `look the word up`.

Предлагаемый payload:

```json
{
  "source_id": "import-1",
  "source_language": "en",
  "target_language": "ru",
  "text": "I looked the word up. My back hurts.",
  "text_sha256": "sha256-of-exact-utf8-text",
  "catalog_snapshot": "en-catalog-17",
  "analysis_profile": "lexical-senses-v1",
  "limits": {"max_candidates": 2000}
}
```

Число 2000 здесь пример конфигурации, не согласованный лимит книги. `source_id` — непрозрачная корреляция, не разрешение читать импорт. Передаются минимально необходимые данные: текст, языки и словарная версия. Email, история занятий и остальные материалы пользователя сервису не нужны.

`text` — точная строка, принятая и сохранённая основным сервером. SHA-256 вычисляется по её UTF-8 байтам. Смещения в результате считаются **в Unicode code points**, не UTF-8 байтах и не UTF-16 code units JavaScript. Диапазон `[start,end)`, нумерация с 0. Анализатор может нормализовать внутреннюю копию, но обязан вернуть координаты исходной строки. Это существенно для акцентов, составных символов и эмодзи.

Парсер файла и извлечение текста — отдельная стадия до этого контракта. Первый предлагаемый клиентский вход — вставленный текст. OCR, скачивание ссылок и распознавание речи не входят автоматически в услугу анализа.

### Доступ анализатора к словарю

Предложение: анализатор использует подготовленный read-only снимок общего словаря указанной версии. Снимок содержит стабильные `entry_id`, `sense_id`, определения, формы, языки и сведения об источниках, но не пользовательские данные. Подготовка снимка входит в административный pipeline языка. При локальном адаптере тот же интерфейс читает каталог через репозиторий основного сервиса.

Если анализатор не знает версию, возвращает `CATALOG_VERSION_UNAVAILABLE`; он не подменяет её молча последней. Приватные карточки основное приложение сопоставляет после анализа в области текущего владельца. Возвращённые ID проверяются: язык, наличие смысла, принадлежность entry и доступность. Ответ модели со случайным UUID не создаёт связь с каталогом.

## 4. Анализ текста: результат и применение

```json
{
  "source_id": "import-1",
  "text_sha256": "sha256-of-exact-utf8-text",
  "analysis_version": "lexical-senses-v1.0",
  "catalog_snapshot": "en-catalog-17",
  "items": [
    {
      "item_key": "item-1",
      "kind": "expression",
      "lemma": "look up",
      "part_of_speech": "verb",
      "definition": "find information in a reference source",
      "translation": "искать в справочнике",
      "resolution": "matched",
      "sense_options": [{"entry_id": "entry-1", "sense_id": "sense-1", "rank": 1}],
      "occurrences": [{"segments": [{"start": 2, "end": 8}, {"start": 18, "end": 20}], "surface": "looked … up", "context_start": 0, "context_end": 21}]
    }
  ],
  "warnings": []
}
```

Это пример одной записи результата, не полный разбор двух предложений. `item_key` стабилен внутри операции и нужен для повторной записи результата. `resolution=matched|ambiguous|unmatched`; при ambiguous перечислены несколько вариантов, при unmatched список пуст и предлагается определение нового смысла. `confidence` может передаваться дополнительно, но не считается гарантией правильности.

Одна запись группирует вхождения **одного предполагаемого смысла**; один `lemma` может иметь несколько записей. `segments` описывает непрерывное слово или части разорванного выражения. Пересекающиеся кандидаты допустимы как альтернативы, но не должны автоматически превращаться в заведомо дублирующие карточки. Правило показа отдельных слов внутри выражения требует проверки качества на реальных текстах.

Основной сервер проверяет хеш текста, диапазоны, типы, лимиты, реальные словарные ID и отсутствие повторов item_key. Контекст извлекает из собственной исходной строки. Границы не должны выходить за строку; segments упорядочены и не перекрываются внутри одного вхождения.

```text
API сохраняет imports + job одной транзакцией
  --> worker вызывает анализатор
  --> анализатор возвращает кандидатов
  --> worker проверяет и сохраняет их атомарно
  --> пользователь выбирает/уточняет значения
  --> основной API применяет отбор одной транзакцией
        |-- существующие смыслы: ссылки на доступные карточки
        +-- недостающие: приватный смысл/карточка + задания медиа
```

Анализатор не делает приватный смысл общим и не создаёт папку. Неоднозначное совпадение не становится подтверждённым из-за высокого score. Выбранные неоднозначные элементы требуют решения пользователя. Тот же `item_key` при повторном получении результата не создаёт новую запись; завершённый анализ не перезаписывает пользовательский отбор.

При лимите размера — `INPUT_TOO_LARGE`. При превышении числа кандидатов — явная ошибка `OUTPUT_LIMIT_EXCEEDED` либо согласованный в будущем режим частичного анализа; молчаливое усечение запрещено. Для книги разбиение на части выполняет оркестратор с сохранением координат и контекста. Точный алгоритм сегментации и поддерживаемые размеры ещё не выбраны.

## 5. Сервис изображений

Изображение привязано к смыслу и ревизии карточки: картинка `back = спина` не подходит автоматически для `back = назад`. По одному написанию кешировать результат нельзя.

```json
{
  "card_id": "card-1",
  "card_revision": 1,
  "sense_id": "sense-1",
  "language": "en",
  "expression": "back",
  "translation": "спина",
  "definition": "the rear part of a person's body",
  "example": "He hurt his back.",
  "generation_profile": "word-illustration-v1",
  "output": {
    "mime_type": "image/webp",
    "width": 512,
    "height": 512,
    "upload_target": "opaque-scoped-upload-target"
  }
}
```

Профиль определяет визуальные ограничения/модель на стороне сервиса. Размер и формат — пример стартовой конфигурации, не новое требование дизайна. Для приватной генерации передаётся только контекст карточки; вся книга не нужна. `upload_target` разрешает запись в выделенный временный ключ текущей операции, не произвольный пользовательский URL. Это может быть ограниченная подписанная загрузка или серверно выданная capability; конкретная реализация выбирается при настройке S3.

Успешный result:

```json
{
  "card_id": "card-1",
  "card_revision": 1,
  "sense_id": "sense-1",
  "asset": {
    "storage_key": "staging/operation-1/image.webp",
    "mime_type": "image/webp",
    "sha256": "sha256-of-file",
    "byte_size": 48216,
    "width": 512,
    "height": 512
  },
  "provenance": {
    "provider": "configured-provider",
    "model_version": "configured-model-version",
    "profile_version": "word-illustration-v1",
    "provider_request_id": "provider-request-1"
  }
}
```

Результат не содержит публичного вечного URL. Основной worker проверяет текущую ревизию/попытку, префикс ключа, фактические размер, хеш, MIME и декодирование изображения. Затем создаёт `media_assets`, связь с черновой ревизией и выполняет публикацию при готовности всех обязательных частей. Имя staging не означает, что ключ будет перезаписан: после принятия он остаётся неизменяемым либо файл копируется в новый неизменяемый ключ до публикации.

Если карточку уже изменили или отменили подготовку, опоздавшее изображение не прикрепляется к новой версии. Сбой после записи в S3, но до фиксации БД, восстанавливается по operation ID и сохранённому результату; новая картинка без необходимости не генерируется. Невостребованный файл удаляется позже сборщиком мусора.

## 6. Сервис озвучки

Единица работы — конкретная произносимая форма, язык, диалект и профиль голоса. Для `look up` озвучивается выражение; для французского варианта с артиклем — вся показанная форма. Разные допустимые артикли оформляются отдельными запросами, но не отдельным прогрессом карточки.

```json
{
  "card_id": "card-fr-1",
  "card_revision": 1,
  "sense_id": "sense-fr-1",
  "form_id": "form-fr-1",
  "text": "la maison",
  "language": "fr",
  "requested_locale": "fr-FR",
  "pronunciation_hint": null,
  "voice_profile": "default-learning-v1",
  "output": {
    "mime_type": "audio/mpeg",
    "upload_target": "opaque-scoped-upload-target"
  }
}
```

`form_id=null` допустим для основной формы карточки. `pronunciation_hint` — проверенная подсказка произношения (например IPA), а не произвольный пользовательский SSML. Основной сервер сверяет text с сохранённой формой ревизии; сервис не должен сам добавлять артикль или менять слово.

Успешный result: `{card_id, card_revision, form_id, spoken_text, actual_locale, ipa?, asset: {storage_key, mime_type, sha256, byte_size, duration_ms}, provenance: {provider, model_version, profile_version, provider_request_id?, source_ref?}}`. Запись из словаря требует проверенного источника и атрибуции. Сервис не выдумывает транскрипцию, если её нет. Основной сервер создаёт `card_pronunciations` и связывает её с тем же файлом для Android и веба.

Для английского предпочтителен `en-GB`. Если запрошенная локаль недоступна, сервис возвращает `VOICE_UNAVAILABLE` с допустимыми альтернативами; решение использовать другую принимает оркестратор отдельной операцией. Возвращённое `actual_locale` должно соответствовать действительности. В интерфейсе такой вариант честно подписан; `en-US` не выдаётся за британский.

Кеш аудио учитывает нормализованную точную форму, язык/локаль, произносительную подсказку, голос/модель и версию профиля. Одинаковое написание при разном произношении не даёт попадание в кеш. Повторное использование приватного результата не должно раскрывать чужой контент; общий кеш допускается только для контента с общей областью доступа. Проигрывание уже готового файла не вызывает TTS.

Недоступность дополнительного диалекта не блокирует основное произношение. Обязательность хотя бы одного готового аудио для публикации карточки остаётся открытой; её нельзя независимо решить в сервисе озвучки. Профиль обязательных медиа задаёт основной сервер.

## 7. Оркестрация подготовки карточки

```text
Основной API        БД/очередь        Worker        Изображения / Аудио
    | сохранить         |               |                   |
    | черновик + job -->|               |                   |
    |<---- 202 ---------|               |                   |
    |                   |<-- аренда ----|                   |
    |                   |               |-- PUT operation ->|
    |                   |               |<-- accepted -------|
    |                   |               |-- GET operation ->|
    |                   |               |<-- файл в S3 ------|
    |                   |<-- проверка и фиксация -----------|
    |                   |<-- publish если всё готово -------|
Клиент GET job -------->|               |                   |
    |<-- ready/failed --|               |                   |
```

Изображение и аудио независимы и могут готовиться параллельно. Результаты фиксируются по отдельности; повтор ошибки озвучки не пересоздаёт уже принятую картинку. `prepare_card` — родительское задание, дочерние `generate_image/generate_audio` хранят отдельные попытки. Если обязательная часть не готова, первичная карточка остаётся generating/failed; исправляемый черновик сохраняется. Для обновляемой карточки остаётся доступной прежняя опубликованная ревизия.

Транзакция создания черновика и jobs общая. Сетевые операции не держат транзакцию БД или её соединение. Транзакция публикации проверяет владельца, смысл, целевую ревизию, готовность файлов и актуальность попытки. Ни AI-ответ, ни запись файла в S3 сами по себе не означают успешную публикацию.

## 8. Ошибки, повторы и отмена

| Ситуация | Действие основного worker |
| --- | --- |
| Тайм-аут после PUT | Сначала GET того же operation ID. Если операция существует — ждать/получить результат; если надёжно отсутствует — повторить исходный PUT. |
| Временная перегрузка / 429 / 503 | Учитывать Retry-After, backoff с jitter, предел попыток и общий deadline. |
| Неверный ввод / неподдерживаемый язык | Не повторять автоматически, показать исправимую причину на карточке/импорте. |
| Неверная схема или чужие sense ID | Не публиковать, `INVALID_SERVICE_RESULT`; ограниченный повтор только по явной политике качества. |
| Отказ провайдера по содержимому | Конечная ошибка с понятным сообщением; автоматический повтор тем же вводом не нужен. |
| Процесс упал | После истечения аренды другой worker получает job; проверяет операцию прежде нового платного вызова. |
| Пользователь отменил | Зафиксировать намерение, передать cancel. Прежде публикации снова проверить флаг. |
| Ответ пришёл после отмены / смены ревизии | Не связывать с текущей карточкой, оставить технический результат для сверки/очистки. |
| Провайдер принял платный запрос, статус неизвестен | Пометить неопределённый исход и проверить provider request ID; не делать бесконечные слепые повторы. |

Идемпотентность operation ID предотвращает повторную публикацию, но не гарантирует отсутствие двойного списания у внешнего провайдера, который её не поддерживает. Осознанная новая попытка после terminal failure использует новый operation ID и учитывается в лимитах. Транспортный повтор использует старый ID. HTTP-разрыв клиентского приложения не отменяет job.

Отмена и публикация сериализуются по заданию. Если публикация успела первой — API сообщает, что операция завершена, и не удаляет готовую карточку под видом отмены. Если отмена зафиксирована первой — поздний worker не публикует результат. Отмена генерации не означает гарантированного возврата стоимости внешнего запроса.

Конкретные тайм-ауты, интервалы опроса и число попыток задаются конфигурацией после измерения провайдеров; они не объявляются SLA. Должны существовать верхние пределы на вход, результат, конкуренцию, число повторов и расходы пользователя/всего приложения.

## 9. Доступ, приватность и эксплуатация

- Внутренние endpoints доступны только основному worker по отдельным сервисным полномочиям. API клиента не проксирует произвольный адрес/метод провайдера.
- Анализатор получает пользовательский текст как данные. Инструкции внутри книги не меняют системные правила, не разрешают внешние запросы и не предоставляют доступ к секретам. Структура ответа проверяется независимо от модели.
- Генераторы пишут только в разрешённые ключи текущих операций. Основной сервер проверяет чтением объекта метаданные ответа, а не доверяет произвольному `storage_key`. Произвольные callback URL не принимаются.
- Приватные тексты, полные промпты, подписанные URL и токены не попадают в обычные логи. Логи содержат request/job/operation ID, этап, длительность, размер, код ошибки, техническую версию и расходы.
- Недоступный генератор не блокирует чтение готовых карточек и обучение. Readiness API не должна проваливаться только из-за остановки AI-сервиса.
- Graceful shutdown прекращает приём новых операций; выполняющиеся операции завершаются в лимите или остаются восстанавливаемыми. Реестр операций нельзя держать только в памяти.
- Сборщик мусора удаляет staged-файлы после защитного срока и проверки отсутствия ссылок, активных операций и действующих снимков. Старые опубликованные медиа сохраняются вместе с поддерживаемыми ревизиями.

Передача пользовательского текста внешнему AI-провайдеру пока не согласована. Контракт допускает как локального, так и внешнего исполнителя; подключение внешнего провайдера требует решения о допустимости и условиях хранения данных. Написание этих интерфейсов само по себе такую передачу не разрешает.

## 10. Проверки контрактов перед внедрением

| Сценарий | Ожидаемый результат |
| --- | --- |
| `bank` в двух значениях | Разные кандидаты смыслов, даже при одной лемме. |
| `look the word up` | Сегменты выражения привязаны к исходной строке и одному смыслу. |
| Текст с emoji/диакритикой | Диапазоны правильно преобразуются в JS-индексы и дают исходный контекст. |
| Два PUT одного ID | Одна операция/файл; другое тело того же ID отклонено. |
| Сбой после записи S3 | Повторная проверка находит файл и завершает фиксацию без лишней генерации. |
| Новая ревизия во время генерации | Старый ответ не перезаписывает новую карточку. |
| Ошибка одного аудио | Готовое изображение не теряется, повторяется нужная часть. |
| Недоступна en-GB | Явная ошибка/согласованный fallback с честной локалью. |
| Анализатор вернул несуществующий sense ID | Результат не создаёт некорректную связь с каталогом. |
| Отмена одновременно с готовностью | Одна однозначная развязка, без скрытой публикации после принятой отмены. |

## 11. Решения, которые ещё нужны

Выбрать провайдеров/локальные модели, допустимость внешней обработки текстов, форматы и размеры источников, качество сопоставления и ручной коррекции, обязательные медиа, сроки хранения и бюджет. Решение о вынесении NLP и TTS в отдельные процессы принимается по окружению и нагрузке; предметные контракты остаются теми же.
